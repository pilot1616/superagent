# 人工单次追加任务执行额度

> 2026-11-21：预算、单轮绑定和审计规则保留；[020](020-centralized-workflow.md) 将可信控制台重试合并为一次人工确认，不再先申请后审批。公开 MCP 仍不能自批额外额度。

## 1. 目标与边界

`maxAttempts` 继续表示计划对每个节点预先批准的执行分配总数，包含首轮，不表示额外重试次数。额度内仍由显式重试请求触发执行，不新增失败自动循环。额度耗尽后允许申请一轮额外执行。人工可重复申请，没有固定累计次数上限；每一轮必须单独审批。

追加只影响指定任务的一轮，不修改计划的 `maxAttempts`、其他节点、依赖验收、资源锁、运行环境启用、计划有效期或发布授权。环境和输入故障仍保留原始分配记录，不删除历史或伪造未执行。

## 2. 请求与审批

1. `task_retry` 对失败、阻塞以及带问题的阻塞报告均可申请。额度内沿用当前计划授权；额度耗尽生成 `retry` 待审批，不立即创建新分配。
2. `task_resume` 在正常恢复审批中，如下一轮超出计划额度，同样明确展示单轮追加，不允许借恢复绕过预算。
3. 追加审批绑定任务 revision、完整范围、计划 ID/version/当前授权指纹、原始额度、已分配轮数和唯一下一轮 generation。禁止模型通过请求字段自批、指定新上限或任意 generation。
4. 控制台审批中心展示追加信息、原始上限与下一轮编号，仍需人类预览并输入完整审批 ID。拒绝、过期、停止或范围/计划授权变化均不执行。
5. 批准时重新检查绑定、有效计划及无不确定状态，再创建一轮分配，双向记录审批 ID 和 assignment ID。保留计划原上限并审计。

## 3. 调度与持久化

调度器对超过原上限的分配，仅接受与该 assignment、任务、generation、计划版本和当前授权指纹完全匹配的已批准追加凭据。不能将一个凭据复用到下一轮、另一任务或修改后的计划。运行环境、暂停、人工 hold、对账、依赖和资源限制仍独立检查。

新增 Assignment 可选 `retryApprovalId`，兼容原数据库 JSON；不迁移或重写历史轮次。待审批请求继续使用已有幂等和 revision 机制。已批准的单轮额度随数据库保存，重启后的执行不确定性仍走原对账流程。

## 4. 控制台与回归

任务详情显示基础额度、已分配轮数和剩余额度；耗尽时重试按钮提示申请人工追加。审批摘要明确“仅追加下一轮、不修改全局额度、可能产生额外模型费用”。

覆盖额度内重试、耗尽后只申请不派发、批准/拒绝/过期、重复请求与重复批准、同一凭据不可复用、任务/计划变更、恢复路径、依赖/人工 hold/运行门禁保持及控制台认证/CSRF。

## 5. 本地 PDF 能力排障与部署

宿主技能不等于 Worker 已导入的技能。项目应显式导入选定的 `pdf-parser` 只读快照，配置现有 Python 和 PDF 库所需的受信任工具目录，验证 Worker 技能发现和实际沙箱解析，不隐式导入全部全局技能或凭据。受审查的工具 PATH 必须显式进入 shell 配置，而非仅在外层进程环境中设置，避免 shell 清洗后退回系统 Python。原始桌面 PDF 仍须人工通过“只读参考资料”预览确认附加；技能导入不会自动开放桌面或启动任务。

配置前备份、停止项目服务并确认无运行或不确定执行。保留模型/provider/认证/子 Agent 配置和历史任务。构建及测试完成后重启项目，报告新的控制台地址和未解决的输入阻塞；不代为人工启用环境、审批追加或重试业务任务。
