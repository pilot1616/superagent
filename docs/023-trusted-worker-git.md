# 023 · 信任 Worker 的本地 Git 写权限

日期：2026-11-21。

## 修改目标

允许 Worker 在服务分配的任务 worktree 和分支中直接执行 `git add`、`git commit`，不再要求等到 GitLab 发布环节才产生本地提交。按用户选择信任 Worker，用执行提示词约束 Git 操作范围，而不是将共享 Git 元数据设为只读。

## 实现范围

1. 执行器解析任务 worktree 的真实 Git common directory，将其单独作为可写目录传入 Worker Runtime；不再放入资料只读列表。
2. Runtime 校验写入目录确实是该 worktree 的 Git common directory，命名权限配置显式授予写权限。有效配置核对使用相同目录，避免权限已开放却被旧检查误判。
3. 根 Worker 指令和每轮任务资源说明同时允许本地暂存和提交；继续限定已分配的 cwd、分支与基线，不重建 worktree、不操作其他任务分支、不擅自改共享配置或执行破坏性 Git 操作。远端 fetch/push、MR、合并目标分支仍由既有服务流程管理。
4. 提交前检查差异，只暂存任务文件，使用已配置或明确提供的身份，不伪造身份；完成后在结构化报告的 summary 中写明实际分支、提交 SHA 和检查结果。启用子 Agent 时，应传递相同约束，由根 Worker 串行管理暂存和提交，避免多个 Agent 同时操作同一 index。
5. 不开放整个宿主目录，不修改主会话权限；资料和技能继续只读，服务状态及凭据继续保护，工具网络维持现状。不新增本地提交审批步骤，也不移除任务启动授权、停止控制或验收机制。

## 信任边界与兼容性

共享 `.git` 可写意味着 Worker 在权限上有能力修改共享分支引用及仓库配置。任务分支范围、禁止破坏性操作是提示词约定，不是强隔离或命令级安全保证。不能再将此模式描述成 Git 元数据只读或任务分支之间有严格权限隔离。

GitLab 发布继续预览实际工作区及 HEAD；已经由 Worker 创建的提交应被复用，不重复创建无变化提交。此次改动不自动合并代码依赖、不迁移旧计划基线、不自动接受结果，也不更改已发布任务。

权限随新 Worker 进程下发，不需要修改所有项目的持久化 profile。运行中 daemon 不会自动加载新代码；部署时需要安全重启对应服务，已有 Worker 进程不会热更新。源码修改不等同于已重装或已重启。

## 验证要求

- 使用真实 Codex 命名沙箱和临时 Git 仓库验证编辑、暂存、提交成功；同时验证参考资料不能写入、其他任务私有状态不能读取。
- 核对 App Server 生效配置及 Git 目录写权限，拒绝非当前仓库的任意写目录；覆盖无附加资料时仍生成 Git 写权限。
- 临时仓库包含两个 worktree，在各自分支顺序提交，确认另一分支及基线不被正常操作改变。
- 验证 GitLab 预览能复用 Worker 本地提交及保留后续未提交修改。
- 执行构建、完整测试及差异检查；不调用真实付费模型、不 push、不修改业务任务。

## 实施与验证结果

- 已实现：任务专属 Git 可写目录下发、真实目录校验、有效配置检查，以及根 Worker / 每轮输入 / 协调 Skill 的一致提示词。资料权限与远端发布流程保持不变。
- 真实 `codex sandbox -P superagent-worker` 在两个临时 worktree 的各自分支完成编辑、`git add`、`git commit`；另一任务分支及主分支保持原先预期值。资料写入和其他任务状态读取仍被拒绝。App Server 配置回读显示当前仓库 Git 元数据为 `write`。
- 发布回归覆盖已提交干净工作区直接复用原 SHA，以及本地提交后又有修改时以该提交为父节点生成后续提交；GitLab API 和 push 使用测试替身，没有远端写入。
- `npm --prefix packages run build`、`npm --prefix packages test` 通过：**261/261，0 失败、0 跳过**。Skill、插件格式校验和 `git diff --check` 通过。
- 没有调用真实付费模型，没有提交本项目改动、安装插件、重启业务服务或调整业务任务。已运行的 Worker 不会热更新；部署需要重启对应服务并重新检查运行环境。
